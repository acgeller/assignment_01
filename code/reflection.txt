The main thing I learned in this assignment came from a debugging experience that turned out to be environmental, not logical. My functions kept returning None in the notebook tests, and I spent an hour or two assuming my logic was broken. Only after I opened bill.py and printed the outputs of tip_amount, grand_total, and split_evenly did I confirm the functions were computing correctly—the real culprit was the kernel I'd selected in the .ipynb.

That experience clarified how return values flow between functions. In 256, I thought print passed values through functions the way return does. This assignment made the distinction concrete: grand_total has to return its value so it can call tip_amount and add to it, and split_evenly needs a real returned total to divide—a print would pass None downstream, the same failure I saw from the kernel.

Two concrete next steps. First, I'll validate results with assertions against known inputs (e.g., assert grand_total(50, 20) == 60.0) instead of relying on the notebook display, and I'll test edge cases like rounding on uneven splits and the ValueError that split_evenly raises when people <= 0. Second, before debugging, I'll confirm the notebook kernel points to the same environment my .py file runs in, with a quick sanity cell at the top, so I don't again mistake a kernel problem for broken logic.
